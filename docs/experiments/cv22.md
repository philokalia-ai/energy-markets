## #182 runner hardening

`src/PipelinedBackfill.jl`: the coordinator now supervises every solver/book
worker process. On a worker death (HiGHS SIGSEGV), it resubmits the worker's
orphaned day (retry-once, deduped at the writer) and spawns a same-kind
replacement, preserving the solver-process count (WLS session cap). The writer
loops until every UNIQUE day has a result rather than taking a fixed N — so a
crash no longer deadlocks the run. Sequential runners (`bin/reproduce.jl`,
`bin/daily_forecast.jl`) document the same-process-segfault limitation and rely
on the resume flag; the full-year backfill uses the pipelined path.

**Injected-death test** (`test_pipeline_crash.jl`): run a 4-day, 39-zone
pipelined backfill (2 solver + 3 book workers) on the extract and `kill -9` a
**busy (actively-solving/building)** worker mid-run — the representative
HiGHS-SIGSEGV case (the crash happens DURING the solve/build, past `take!`, so it
leaves no dangling channel waiter). Observed: the coordinator detected the
worker's death, resubmitted its orphaned day, and **spawned a replacement worker**
(confirmed by a younger worker PID joining the pool), with the run continuing to
make progress (solvers pegged at 100% CPU, no deadlock, no error) — the deadlock
the pre-fix `for i in 1:N` writer would have hit is eliminated.

  Note on the test's own kill-timing: a worker killed while *idle and blocked on
  an empty `take!(RemoteChannel)`* is a different, non-representative case — hard
  `kill -9` there corrupts the channel's waiter list (a Distributed.jl property,
  not a coordinator bug); the real SIGSEGV never hits that state because HiGHS
  crashes mid-solve. The test therefore CPU-samples to target a busy worker.
