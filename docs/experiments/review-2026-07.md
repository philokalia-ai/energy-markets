# Code review, July 2026 — findings, what shipped, what did not

A full-codebase review (four parallel scans over the merit-order core, the MPCC
solver, the parallel orchestration and the data layer, plus a manual pass over
the daily forecast worker). Ranked findings below, each with its verification
status. This PR ships **only the price-inert half**; the price-changing half is
recorded here with a reproduction so it can be scheduled as its own
code_version with a backfill.

## Shipped (all price-inert, guarded bit-identical)

| Fix | File | What was wrong |
|---|---|---|
| Pool permit released on every path | `src/db/postgres_core.jl` | `withdb` had no `try/finally`. Every exception — statement timeout, killed backend, a UniqueViolation — leaked one pool permit; after `poolsize` of them EVERY query in the process blocked forever with no error and no log. `sql2df_with_retry`'s error path calls `preinit_pool`, which acquires all permits at once, so a single leak could hang the run inside its own retry handler. |
| Completeness, not status names | `src/mpcc/solver.jl` | The period-decomposition status merge classified `:optimal` / `:error` / `:infeasible` and let everything else fall through to `else :time_limit` — the bucket the caller treats as USABLE. `:numerical_error`, `:other_error`, `:memory_limit`, `:almost_optimal` are all reachable and all landed there, so a day missing an hour was saved as a complete record. Now every node×period cell is asserted; a missing cell is `:error`. |
| Retry exhaustion fails, does not hang | `src/PipelinedBackfill.jl` | The crash supervisor resubmits an orphaned day once. If the retry also died the day never produced a result and the writer (`while length(seen) < N`) parked on `take!` forever with every worker idle and the feeder drained — a silent hang losing the rest of the run. Segfaults are input-dependent, so a day that crashed once tends to crash again. Same treatment when no worker of a kind can be respawned. |
| Resume is zone-count aware | `src/PipelinedBackfill.jl` | A zone whose book build fails is dropped and the day is written with 38 of 39 zones, printed `DONE`. Resume's verdict was "any row for that day", so the short day was permanent. Now a day counts as saved only when every requested zone is present (free — same grouped scan, one more aggregate). |
| Pass-2 failure is visible | `src/PipelinedBackfill.jl` | A pass-2 solve exception was swallowed **entirely** and reported as a successful day. A 1,300-day record gave no way to tell which days are silently pass-1 only. The sequential path warns; now so does this one. |
| Prices saved from the prices | `src/PipelinedBackfill.jl` | The writer iterated the pass-2 book's node list while saving `r.final`, which can be the pass-1 result. A zone that cleared in pass 1 but dropped out of the pass-2 rebuild had its prices silently discarded. |
| All-skipped date ≠ failure | `src/clearing/batch_runners.jl` | With `skip_existing=true`, five already-complete days in a row tripped the "5 consecutive failures ⇒ systematic issue" early termination, so resuming a partly-finished range stopped after five days and reported the rest as failures without attempting them. |
| RES coverage gated like load | `bin/daily_forecast.jl` | The weather track applied "partial publications must read as not-yet-published" to the TSO's RES but not to its own: `weather_scenario` zeroes the ENTSO-E forecast and injects `get(zone_pred, hour, 0.0)`, so an hour the model could not predict cleared at **zero wind+solar**. That is the 2026-07-12 failure (a day frozen with most of Germany's solar missing, corr −0.50) reintroduced from the model side — and vintages are immutable, so it could never be corrected. |
| Book flush scoped to its day | `bin/daily_forecast.jl` | The `_BOOKS` accumulator is never emptied, so `flush_books!` wrote every previously-cleared UTC day into each per-day parquet, stamped with the wrong `market_date` and growing quadratically over a run. |
| `DISABLE_CV23` reverts all of cv23 | `src/merit_order/zone_profiles.jl` | The switch claimed to "revert exactly to cv22 main" but the FR-cap half of cv23 was reachable only through `DISABLE_FRCAP`, so the cv23 byte-identity guard compared the wrong pair. |
| Transfer verification can fail the run | `bin/transfer_results_to_postgres.jl` | `run_verify`'s verdict was discarded: a transfer whose zone-month checksums disagreed still printed `DONE` and exited 0. Also documents the flow delete's wider (non-mode-scoped) blast radius. |

## NOT shipped — needs its own code_version and a backfill

### 1. Every bidirectional border carries 2× its offered ATC

`src/Network.jl` (`get_zone_pairs`) + `src/mpcc/solver.jl` (flow variables).

ENTSO-E publishes one row per direction, so a coupled border produces both
`(A,B)` and `(B,A)` keys in `capacity_forward`. `get_zone_pairs` returns **both
orientations** and the solver builds an independent full-range flow variable for
each, with nothing linking them. Zone A's balance carries `+flow[(A,B)] −
flow[(B,A)]`, so the net transfer ranges over `[−2·cap_BA, +2·cap_AB]`. On a
congested border it is not merely permitted but *forced*: `(A,B)`'s forward rent
pins its flow to `+cap`, `(B,A)`'s pins its own to `−cap`.

The builder's own docstring states the intended model — ONE variable per
unordered border, `flow[A,B] ∈ [−capacity_backward, +capacity_forward]`.

Reproduction (`test/test_review_2026_07.jl`, DB-free, HiGHS):

```
Bidirectional border (the real data shape):  net A→B = 200.0 MW   ❌ offered ATC = 100 MW
Single orientation (what the old tests build): net A→B = 100.0 MW   ✅
```

Scale in production, from the committed 39-zone run logs: `Forward capacities:
2016 entries` ÷ 24 periods = 84 directed pairs, `Bidirectional links: 1904` ÷ 24
≈ 79 — so **~40 of ~44 physical borders** carry double capacity in the published
record. Only ~4 directed pairs are genuinely unidirectional.

Why no test caught it: every multi-zone test builds `TransferCapacity` by hand
with a single forward key, i.e. the control arm above.

Fix: canonicalise `get_zone_pairs` to one orientation per unordered border
(`s < d`), keeping the ± bounds. Do **not** instead clamp each directed variable
to `≥ 0` — an idle border would then sit at both directions' backward limits and
both congestion rents could turn on at once.

Consequence to measure, stated as a hypothesis: the footprint is over-coupled,
so price separation appears only above twice the true capacity and congestion is
systematically under-priced. That is consistent with the converging finding of
the PL/NL/IT-NORTH diagnoses — that roughly half of each zone's evening error is
imported through the coupling — but the direction and size of the correction
must be measured on the coupled footprint against settled prices, at the
standing bar (blind windows, ≥8 days/season, neighbours in the gate).

### 2. The pipelined backfill is not ex-ante — it uses `:d0` same-day flows

The EU-footprint flow default (`:v3` since cv19) is resolved **inside**
`run_multi_zone_market_clearing`. The book workers call `mz_build_books`
directly, which has no such resolution, so they use the process-wide
`FLOW_ASOF_MODE` — `:d0`, same-day **observed** flows — unless
`EUPHEMIA_FLOW_ASOF_MODE` happens to be in the environment. Of the pipeline
drivers only `bin/cv18_backfill_offline.jl` sets it: not
`bin/reproduce.jl --pipeline`, not `bin/eu_calibration_run.jl` under
`PIPELINE=true`.

Consequences: the same `reproduce.jl` invocation produces different prices with
and without `--pipeline`; `test/scripts/pipeline_identity.jl` compares a `:v3`
sequential arm against a `:d0` pipelined arm, so its "bit-identical" claim does
not mean what it says; and any record produced through the pipeline peeked at
delivery-day flows.

Fix: `mz_build_books` must take `ex_ante_mode` and apply the same scoped
resolution, or (better) both callers must go through one shared
`mz_resolve_policy(...)` that owns the flow mode, the decomposition policy and
the `:p95` fallback. Marked `@test_broken` in the new test file.

**Open question for the record**: which published records were built through the
pipeline with the env unset. The flow mode is not stored on the rows, so this
has to be settled by re-clearing a sample day both ways and comparing against
the stored prices.

### 3. ISO-week / calendar-year mismatch in the reservoir queries

`src/merit_order/fleet_data.jl` pairs `iso_week = Dates.week(day)` (ISO-8601)
with `iso_year = year(day)` (calendar). They disagree on 2-3 days per year.
On **2023-01-01** — day one of the canonical record — the predicate resolves to
`(2023, week 51)`, i.e. a reservoir level ~11.5 months **after** the delivery
day (an 11-month lookahead); `get_reservoir_drawdown` takes both its current and
max from that future year. On 2025-12-29..31 the same mismatch reaches back a
full year instead. Fix: `iso_year = year(day - Day(dayofweek(day) - 4))`.
Companion: the cv22 wrap `mod1(iso_week + d, 52)` can never emit week 53.

### 4. The fleet's recent-generation probe includes the delivery day

`src/generators/registry.jl` bounds the 60-day probe with
`< $2::timestamp + INTERVAL '1 day'`, i.e. through the end of market day D,
while the sibling probe 100 lines earlier correctly uses `< $1::timestamp`. A
unit whose registry validity is stale enters day D's fleet **because it
generated on day D**. One character, but it changes prices on the days it fires,
so it belongs with the batch above.

## Also found, lower severity (not fixed here)

- `solve_mpcc_market_clearing` abandons the competitive price reconstruction for
  a whole period when the rent-sign check fails, with **no warning and no field
  on the result** — the published price silently changes provenance to the
  solver's arbitrary interior point.
- The marginal-price accumulator mixes supply-max and demand-min in one
  variable, seeded by whichever marginal order is enumerated first; a component
  with marginal orders on both sides is decided by book assembly order.
- The whole MPCC robustness ladder and the IIS diagnostic are Gurobi-gated,
  while the canonical mode has run on HiGHS since cv20 — the ladder is dead code
  in the configuration that produces the record.
- Day-keyed caches (`_OUTAGE_DAY_CACHE`, the `get_generators` memo,
  `_NET_IMPORTS_DAY_CACHE`, …) are unbounded and never evicted;
  `clear_fleet_data_caches!` has no call sites. A 1,300-day backfill grows
  monotonically per worker.
- No cache is keyed on the backend, and `eu_duckdb_parity.jl` clears only four
  of them — so the DuckDB arm can reuse the Postgres arm's net imports, p95 and
  hydro availability, which are exactly the quantities the documented ≤2e-12
  residual comes from.
- `MAX_PLAUSIBLE_UNIT_MW` (cv24) is applied in `registry.jl` but not in
  `fleet_data.jl`'s `get_installed_capacity_by_type`, which feeds the
  `:installed` fleet-truth denominators and FR's nuclear availability.
- `normalize_fuel_type_name` collisions in `book_build.jl` keep whichever
  spelling comes last in Dict order instead of combining (the sibling
  aggregation in `fleet_data.jl` sums).
- Postgres `save_energy_prices` inserts in independent 100-row transactions, so
  a mid-write failure leaves a permanent partial day (the DuckDB writer does one
  DELETE + one bulk INSERT).

## Simplicity verdict

Not length — placement. ~140 lines of pure arithmetic that determines every
published price (the competitive price reconstruction in `solve_mpcc_market_`
`clearing`) can only execute behind a live MIP solve, which is why two of the
findings above live there untested. Extracting it as a pure function taking
pre-extracted flow values would be numerically inert and make all of it
unit-testable.

Second: 22 of `create_merit_order_book`'s 39 keyword arguments shadow
`ZoneProfile` fields, each with a `x === nothing ? profile.x : x` line and a
docstring entry. `with_profile` already exists and collapses the lot. Deferred
to its own PR — it is a ~100-site rename inside the price core and deserves a
wider guard than two days.

Third: 94 `try` blocks against 56 `error(` calls. Findings 2, 3, 5 and 6 of the
shipped table are all the same shape — a failure recorded as a success.
